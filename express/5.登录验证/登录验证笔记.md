# 登录验证设计笔记

## 一、整体流程

```
【登录】
客户端 POST /api/admin/login { loginId, loginPwd }
    ↓
adminService.login → 验证账号密码 → 返回 admin（已脱敏）
    ↓
路由层 encrypt(secret, String(admin.id)) → 生成加密 token（iv+密文）
    ↓
res.cookie("token", token) → 浏览器自动保存并在后续请求带回
    ↓
res.send(管理员信息)

【后续请求】
客户端请求带 cookie: token=xxxx
    ↓
tokenMiddleware 拦截需要鉴权的接口
    ↓
decrypt(secret, token) → 切出 iv → 解密得到 userId
    ↓
验证 userId 有效 → req.userId = userId → next()
    ↓
后续接口从 req.userId 拿到当前登录用户
```

### 各文件职责

| 文件 | 职责 |
|------|------|
| `util/crypt.js` | 加密/解密函数，iv 自包含在密文里 |
| `routes/api/admin.js` | 登录接口，验证成功后下发加密 token |
| `routes/tokenMiddleware.js` | 拦截需要鉴权的接口，解密验证 token |

## 二、加密方案：AES-128-CBC + 自包含 iv

### 2.1 核心思想

AES-CBC 模式需要三个东西：**密钥(secret) + iv + 密文**。其中：

- **secret**：必须保密，只在服务器
- **iv**：不用保密，但必须每次随机、和密文绑定在一起
- 解密时把 iv 从 token 字符串里切出来用，服务器不需要"记住"上次的 iv

### 2.2 为什么 iv 不需要保密

iv（初始化向量）的作用是让"相同明文用相同密钥加密产生不同密文"，防止攻击者通过对比密文推测明文模式。iv 只需满足：

- **不可预测**（随机生成）→ `crypto.randomBytes(16)`
- **唯一**（每次加密不同）

iv 公开没关系，缺了 secret 照样解不开。这是密码学常识——iv、salt、nonce 这类值都是可以公开传输的。

### 2.3 为什么 iv 要和密文拼在一起

服务器是无状态的，两次请求之间记不住任何东西。如果只把密文传给客户端、iv 留在服务器内存里，下一次请求就拿不到原来的 iv 了（必然 `bad decrypt`）。

把 iv 拼进 token 字符串，让浏览器替你"保管"一回合 iv，下次请求原样带回来，服务器再切出来用——这就是无状态加密的标准套路。

### 2.4 加密解密实现

```javascript
import crypto from "crypto";

export const secret = Buffer.from("asdfghjklzxcvbnm"); // aes-128 需要 16 字节密钥

// 加密：返回 iv(hex) + 密文(hex)，前 32 字符是 iv
export function encrypt(secret, str) {
    const iv = crypto.randomBytes(16); // 16 字节随机 iv
    const cipher = crypto.createCipheriv("aes-128-cbc", secret, iv);
    let encrypted = cipher.update(str, "utf-8", "hex");
    encrypted += cipher.final("hex");
    return iv.toString("hex") + encrypted; // 32 字符 iv + 密文
}

// 解密：前 32 字符切出 iv，剩下当密文
export function decrypt(secret, signed) {
    const iv = Buffer.from(signed.slice(0, 32), "hex"); // 取出 iv
    const encrypted = signed.slice(32);                  // 剩下是密文
    const decry = crypto.createDecipheriv("aes-128-cbc", secret, iv);
    let decried = decry.update(encrypted, "hex", "utf-8");
    decried += decry.final("utf-8");
    return decried;
}
```

### 2.5 单位换算（容易混）

| 单位 | 数量 | 说明 |
|------|------|------|
| 字节 (byte) | 16 | `randomBytes(16)` 的参数 |
| 位 (bit) | 128 | 1 字节 = 8 位，AES 块大小固定 128 位 |
| hex 字符数 | 32 | 1 字节转 hex 占 2 个字符，16 × 2 = 32 |

所以解密时 `slice(0, 32)` 切的是 **32 个字符**（对应 16 字节），不是 16。

## 三、登录接口下发 token

```javascript
import { encrypt, secret } from "../../util/crypt.js";

adminRouter.post("/login", async (req, res) => {
    const { loginId, loginPwd } = req.body;
    const result = await adminService.login(loginId, loginPwd);

    if (result) {
        // 加密用户 id 作为 token，注意 id 是 number 要转 string
        const value = encrypt(secret, String(result.id));
        res.cookie("token", value, {
            path: "/",
            maxAge: 3600 * 1000,  // 1 小时
            httpOnly: false
        });
        res.send(normalHandeler(result));
    } else {
        res.send(errHandeler("账号或密码错误", 400));
    }
});
```

### 要点

1. **`result.id` 是 number**，`cipher.update` 只接受 string/Buffer，必须 `String(result.id)`
2. **cookie 的 `maxAge` 单位是毫秒**，`3600 * 1000` 才是 1 小时
3. **不要写死 `domain`**：留空会自动匹配当前请求的 host，localhost 和 127.0.0.1 都通用

## 四、Token 中间件

### 4.1 path-to-regexp v8 的 API 变化

Express 5 默认带 path-to-regexp v8，`pathToRegexp()` **不再返回 RegExp**，而是返回 `{ regexp, keys }` 对象。老代码 `reg.test(path)` 会报 `reg.test is not a function`。

正确用法是改用 `match()` 函数：

```javascript
import { match } from "path-to-regexp";

// v8：match 返回一个函数，调用它传实际路径
const matcher = match("/api/student/:id");
matcher("/api/student/123");  // { path, params: { id: '123' } }
matcher("/api/other");         // false
```

### 4.2 完整中间件实现

```javascript
import { errHandeler } from "./getSendResult.js";
import { match } from "path-to-regexp";
import { decrypt, secret } from "../util/crypt.js";

// 预编译匹配器：启动时只编译一次
const config = [
    { method: "POST", path: "/api/student", matcher: match("/api/student") },
    { method: "PUT", path: "/api/student/:id", matcher: match("/api/student/:id") }
];

export function tokenHandel(req, res, next) {
    // 1. 判断当前请求是否需要鉴权
    const result = config.filter((api) => {
        return !!api.matcher(req.path) && api.method === req.method;
    });
    if (result.length === 0) {
        next();  // 不需要鉴权，放行
        return;
    }

    // 2. 取 token（cookie 优先，authorization 头兜底）
    let token = req.cookies.token;
    if (!token) {
        token = req.headers.authorization;
    }
    if (!token) {
        res.status(403).send(errHandeler("token不存在", 403));
        return;
    }

    // 3. 解密 token，失败返回 403（必须 try/catch，否则 500 挂死）
    try {
        const userId = decrypt(secret, token);
        req.userId = userId;  // 挂到 req 上供后续接口用
        next();
    } catch {
        res.status(403).send(errHandeler("token无效或已篡改", 403));
    }
}
```

### 4.3 要点

1. **匹配器要预编译**：把 `match(path)` 放进 config 数组，启动时只编译一次。放在请求处理函数里每次请求都重新编译，有性能浪费
2. **解密必须 try/catch**：token 被篡改时 `decipher.final()` 会抛 `bad decrypt`，不捕获会导致 500 挂死
3. **不要只判断 token 非空**：只判断"有没有"不解密等于没验证，随便填个 "abc" 都能通过
4. **挂载 userId 到 req**：后续接口可直接用 `req.userId`，不用重复解密

## 五、踩过的坑

### 坑一：iv 拼接时 Buffer 隐式转换

```javascript
// ❌ 错误：iv 是 Buffer，+ 字符串会触发 toString()，默认是 utf-8 不是 hex
return iv + encrypted;  // 产生二进制乱码字符 → ERR_INVALID_CHAR

// ✅ 正确：显式转 hex
return iv.toString("hex") + encrypted;
```

Buffer 的默认 `toString()` 是 utf-8 解码，会把随机字节解释成乱码字符（控制字符、换行等），HTTP 头不允许这些字符。

### 坑二：解密切错 iv 长度

```javascript
// ❌ 错误：按 16 切（那是字节数，不是字符数）
const iv = signed.slice(0, 16);  // 只切了 8 字节，iv 缺一半 → bad decrypt

// ✅ 正确：按 32 切（16 字节 × 2 = 32 个 hex 字符）
const iv = Buffer.from(signed.slice(0, 32), "hex");
```

### 坑三：解密时用错变量

```javascript
// ❌ 错误：把整个 iv+密文 当密文解
decry.update(signed, "hex", "utf-8");

// ✅ 正确：用切出来的 encrypted
decry.update(encrypted, "hex", "utf-8");
```

### 坑四：cookie 的 domain 不匹配

```javascript
// ❌ 请求 127.0.0.1 但 cookie domain=localhost，浏览器视为不同域不保存
res.header("set-cookie", `token=${id}; domain=localhost; ...`)

// ✅ 用 res.cookie + 不写死 domain
res.cookie("token", value, { path: "/", maxAge: 3600 * 1000 });
```

### 坑五：nodemon watch 不递归子目录

```json
// ❌ 只监听根目录的 js，改 routes/ 下的文件不重启
"watch": ["*.js"]

// ✅ 递归监听所有子目录
"watch": ["**/*.js"]
```

### 坑六：错误中间件吞掉错误

```javascript
// ❌ 错误中间件不 console.error，控制台一片寂静
// ❌ errHandeler 直接把 Error 对象塞进 msg，JSON.stringify(Error) === '{}'
export function errorMiddleware(err, req, res, next) {
    if (err) {
        res.status(500).send(errHandeler(err));  // msg 变成空对象 {}
    }
}

// ✅ 打印堆栈 + 提取 message
export function errorMiddleware(err, req, res, next) {
    if (err) {
        console.error(err);  // 控制台显示完整堆栈
        res.status(500).send(errHandeler(err));
    }
}

export function errHandeler(err = "server Internal error", code = 500) {
    return {
        code: code,
        msg: err instanceof Error ? err.message : err,  // Error 取 message
    };
}
```

Error 对象的 `message`、`stack` 是不可枚举属性，`JSON.stringify(new Error("xxx"))` 结果是 `"{}"`。

## 六、待完善

### 6.1 解密后应验证 userId 有效性

当前解密成功就放行，但解密出来的 id 可能对应已删除的管理员。建议解密后查库确认：

```javascript
try {
    const userId = decrypt(secret, token);
    // 格式验证
    if (!/^\d+$/.test(userId)) {
        return res.status(403).send(errHandeler("token格式错误", 403));
    }
    // 存在性验证
    const admin = await getAdminById(userId);
    if (!admin) {
        return res.status(403).send(errHandeler("身份已失效", 403));
    }
    req.userId = userId;
    req.admin = admin;  // 查出来的对象也挂上，后续接口不用重复查
    next();
} catch {
    res.status(403).send(errHandeler("token无效或已篡改", 403));
}
```

### 6.2 token 没有自带过期时间

cookie 的 `maxAge` 到期后浏览器不带 cookie，但别人手动复制 cookie 值塞进 `authorization` 头，中间件照样能解密通过。加密 token 本身没有过期信息——这是 JWT 会把 `exp` 写进 payload 的原因。

### 6.3 secret 应从环境变量读取

```javascript
// ❌ 硬编码，提交 git 就泄露
export const secret = Buffer.from("asdfghjklzxcvbnm");

// ✅ 从环境变量读
export const secret = Buffer.from(process.env.SECRET_KEY, "hex");
```

### 6.4 config 鉴权范围需补全

当前只配了 student 的 POST 和 PUT，DELETE 和其他模块（admin/book/class）的增删改没有鉴权。按业务直觉，删除这种破坏性操作更应该鉴权。
